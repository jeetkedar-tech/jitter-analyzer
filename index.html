The four ideas behind the project

Latency

Time a packet takes from sender to receiver. Above about 150 ms one-way, conversation starts to feel awkward because people talk over each other.

Jitter

Variation in latency from one packet to the next. Packets sent evenly arrive unevenly, which makes audio choppy unless a buffer smooths it.

Packet loss

Packets that never arrive, usually from congestion. Voice gets gaps and video freezes or blocks, since real-time media is not retransmitted.

QoS

Methods that protect real-time traffic: marking voice and video packets (DSCP), giving them priority queues, and limiting bulk traffic.

How the analyzer works

  1. Generate packets. One packet every 20 ms for voice, every 33 ms for video, 300 packets per run.
  2. Apply the network. Each packet gets delay = latency + random jitter, and may be dropped (random or bursty).
  3. Apply the jitter buffer. Any packet arriving after its playout deadline (latency + buffer) counts as lost.
  4. Measure. Average delay, RFC 3550 jitter, loss, late packets and audio glitches or video freezes per minute.
  5. Estimate quality. The ITU-T G.107 E-model turns delay and effective loss into an R-factor, then a MOS score from 1 to 5.

Scope and next steps

This version is a frontend-only simulation, so it runs entirely in the browser with no server. The packet delays are generated by a random model, not measured from a real call.

A full version would add a backend or WebRTC getStats() to read real jitter, round-trip time and packet loss from a live call, then feed those numbers into the same E-model calculation used here.
